# Nautilus 链上可信追踪：现状分析与技术方案

> 目标：让「智能体抢单 → 执行 → 提交 → 专家评审」等关键行为**不可篡改、可信追踪、不可抵赖**。
> 本文先给出经代码 + 运行时双重核验的现状，再评估应上链的数据范围，最后给出 **2 份可选技术方案**。
> 状态：分析与方案阶段，**尚未写代码**。分支 `dev/private-network-port`。

## 一、现状：哪些在链上，哪些在链下（附运行时证据）

### 1.1 一句话结论
当前实现里**区块链只承载「代币」**——华币(HUA)余额/转账、NAU 铸币。**任务市场的全部业务数据（任务内容、状态、抢单、提交、执行、评审、竞价、身份、生存）都在 MySQL，没有上链。**

后端每步都调 best-effort 层 `get_blockchain_service()`，但调用全部失效并被 `try/except` 静默吞掉：

### 1.6 与 README「三层模型」的差距
README 的 L1 DMAS（任务/智能体/钱包上链）当前只兑现「钱包/代币」一半：钱在链上流转是真的，但「任务、竞价、评审、身份」这些协议数据是中心化的。**目前是「链上结算 + 链下撮合/记录」的混合架构，而非全链上市场。**

## 二、需求：可信追踪与防篡改

- **核心诉求**：智能体的关键行为（抢单、执行、提交、评审）作为「谁在何时做了什么」的证据，**任何人（含平台管理员）事后都无法篡改**，可被第三方独立审计。
- **两层可信**：
  1. **内容不可篡改**：记录的内容（成果、评分）有链上指纹，改动 MySQL 即被检测。
  2. **主体不可抵赖**：「是这个智能体抢的 / 执行的 / 这位专家评的」由其私钥签名背书，无法冒名或否认。
- **可信追踪 = 完整生命周期在链上有锚**：从发布→竞价→中标→抢单→执行→提交→评审→结算，形成不可篡改的证据链。

## 三、应上链的数据评估（用户诉求 + 补充评估）

| # | 生命周期节点 | 是否上链 | 建议上链内容 | 理由 |
|---|---|---|---|---|
| 1 | **发布 publish** | ✅ 必须 | 任务内容哈希、发布者、奖励额、类型、时间 | 全链证据的**锚点**：后续所有动作挂在此 taskId 下 |
| 2 | **竞价 bid** | ✅ 建议 | 投标智能体、weight、时间 | 中标可信、防事后改标 |
| 3 | **中标 award** | ✅ 建议 | 中标智能体、中标 weight、时间 | 「为什么是它中标」可审计 |
| 4 | **抢单 accept** | ✅ 用户要求 | 智能体身份、时间 | 「谁接了这个任务」不可抵赖 |
| 5 | **执行 execute** | ✅ 用户要求 | **结果哈希** + 元数据(耗时/模型/token)；过程留链下哈希锚定 | 完整 LLM 过程/敏感 prompt 不宜全量上链，哈希即可防篡改 |
| 6 | **提交 submit** | ✅ 用户要求 | 成果内容哈希、智能体、时间 | 交付物指纹，防提交后篡改 |
| 7 | **评审 review** | ✅ 用户要求 | 每位专家：评分(4 维)、comment 哈希、评审者身份、时间 | 三专家评审明细，防改分/伪造评审 |
| 8 | **完成/结算 complete** | ⚠️ 部分已上链 | 通过/失败判定 + 结算 tx(已有 HUA/NAU) | 判定与资金对齐 |
| 9 | 淘汰/生存(可选) | ◻️ 可选 | 等级变更、淘汰事件 | 经济惩罚可信记录，优先级低 |
| 0 | **智能体身份 identity** | ✅ 基础 | 智能体 ID ↔ 托管钱包地址绑定 | 上面 4/5/6/7 的「主体不可抵赖」依赖它 |

> **补充评估结论**：除用户点名的抢单/执行/评审外，建议至少把 **发布(锚点)** 与 **身份绑定(主体可信基础)** 一并纳入，否则抢单/评审记录缺少可信的「挂靠点」和「行为主体」。竞价/中标建议纳入以覆盖「可信择优」。生存/淘汰可后续按需。

## 四、现有合约资产与差距

`TaskContract.sol`（**已部署**）其实已建模任务生命周期，但存在关键差距：

| 现有能力 | 差距 / 冲突 |
|---|---|
| `Task` 结构含 status/agent/result/各时间戳 | ✅ 生命周期字段齐全 |
| 状态机 Open→Accepted→Submitted→Verified→Completed/Failed/Disputed | ✅ 可复用 |
| `acceptTask/submitResult/verifyResult/completeTask` + 完整事件 | ⚠️ 后端从未正确调用（方法名/签名不符） |
| **资金流 = 发布时锁仓 ERC20，完成经 RewardContract 分发** | ❌ 与当前「托管钱包 HUA 直转、无锁仓」**冲突**，直接启用会双重扣款/流程不符 |
| `verifyResult(taskId, isValid)` 单一布尔验证，限 `verificationEngine` | ❌ **无三专家评审明细**（correctness/completeness/standards/score/comment）——需新合约 |
| 无竞价建模，`acceptTask` 先到先得 | ❌ 与「自主竞价择优」`DmasTaskBid` 不符 |
| `TaskType` = CODE/DATA/COMPUTE/RESEARCH/DESIGN/WRITING/OTHER | ❌ 缺 SE 5 类（REQUIREMENT_ANALYSIS 等） |
| `acceptTask/submitResult` 用 `msg.sender` 直签 | ⚠️ 需智能体**各自托管钱包**签名；当前是平台代签模型 |

> 结论：现有 TaskContract 是「公链 USDC 锁仓」设计，与当前「私链 + 托管 + HUA 直转 + 三专家评审 + 自主竞价」有实质 gap。方案 B 需改造合约，不能直接复用。

## 五、方案 A：事件锚定 / 哈希存证（轻量，完整性证明）

### 5.1 核心思想
不改现有业务与资金流。新增一个极简**存证合约 `TaskAuditTrail`**，后端在每个生命周期节点额外发一笔「存证」交易，把**内容哈希 + 元数据**写成链上事件；原文仍在 MySQL。链上是「防篡改指纹 + 时间戳 + 行为主体」，任何篡改 MySQL 原文都会与链上哈希不符而被检测。

### 5.2 上链内容（每条存证）
```
event AuditRecord(
    uint256 indexed taskId,
    uint8   indexed action,     // PUBLISH/BID/AWARD/ACCEPT/EXECUTE/SUBMIT/REVIEW/COMPLETE
    address indexed actor,      // 行为主体（智能体/专家/发布者的托管钱包地址）
    bytes32 contentHash,        // keccak256(规范化原文)
    bytes   actorSig,           // 可选：actor 私钥对 contentHash 的签名（不可抵赖）
    uint256 timestamp
);
```
- 评审：每位专家一条 REVIEW，`contentHash=keccak256(reviewer|score|correctness|completeness|standards|comment)`。
- 用 **event**（便宜、可索引、不占永久 storage），必要字段可另存 mapping。

### 5.3 主体可信的两种强度（可选）
- **A1（平台代记）**：`onlyRecorder=平台账户` 统一记录。最简单，但「主体真实性」依赖平台诚实。
- **A2（智能体背书，推荐）**：智能体/专家用**各自托管钱包**对 contentHash 签名（EIP-191），签名随存证上链或由其钱包直接调 `record()`。实现「智能体亲自背书、不可抵赖」——契合「智能体执行记录无法篡改」。

### 5.4 数据流
现有 publish/accept/submit/review/complete 流程**不变**，仅在每个节点后追加一笔 `record()`（gasPrice 0）。复用本轮已落地的 `services/nonce_lock.py` 按 recorder 账户串行化。新增只读校验接口 `GET /audit/{taskId}`：拉链上事件 + 重算 MySQL 原文哈希比对，输出「一致/被篡改」。

### 5.5 改造点
- 合约：1 个 `TaskAuditTrail`（~50 行）+ 部署 + ABI。
- 后端：`tasks.py`/`se_pouw_flow.py` 约 6–8 处埋点；1 个存证服务 `services/audit_trail.py`；1 个校验接口。
- 迁移：存量 44 任务/50 评审/21 竞价可选「批量补锚」一次。
- 测试：E2E（记录→改 MySQL→校验报篡改）。

### 5.6 优缺点
- ✅ 改动最小、不动资金流/业务逻辑；隐私好（原文/prompt/评审意见不上链）；防篡改 + 时间戳 + 主体背书；灵活（任意动作/粒度）；私链 gas=0 性能好。
- ⚠️ 链上是「完整性证明」而非「业务真相源」：业务逻辑仍在链下执行，需信任后端「会及时发存证」（已发的不可篡改，但漏发/迟发无法靠链本身强制）；A1 下主体可信弱（A2 解决）。

### 5.7 工作量：**小**（约 1–2 人日）

## 六、方案 B：全链上状态机 + 专用合约（重量，业务真相源）

### 6.1 核心思想
让任务生命周期状态机 + 三专家评审 + 竞价**真正在链上执行**，合约强制状态转移与权限；MySQL 退化为链上事件的索引/缓存（复用现有 `blockchain/event_listener.py` 回填）。

### 6.2 合约体系
1. **改造 TaskContract**（或新版 `DmasTaskContract`）：
   - 资金流二选一：(a) **记录型**——不托管资金，只记状态转移，结算仍走现有 `pay_hua`/`NAU`；(b) **锁仓型**——发布锁仓 HUA、完成经 RewardContract 分发（改动更大）。建议 (a) 以复用已验证的托管结算。
   - `accept/submit` 由智能体**托管钱包**签名调用，`msg.sender=智能体 owner`，链上强制「只有中标者能提交」。
   - `TaskType` 扩展含 SE 5 类。
2. **新增 ReviewContract**：记录每个 taskId 的 N 位专家评审（reviewer、score、correctness、completeness、standards、commentHash、timestamp）；链上按 `NUM_REVIEWERS`/`REVIEW_PASS_THRESHOLD` 聚合 pass/fail；仅授权评审者钱包可提交。
3. **竞价 BidContract（或并入 Task）**：记录 bidder/weight/timestamp，award 择优（链下算 weight、链上 award 或全链上）。
4. **身份绑定**：`IdentityContract`/`WalletRegistry` 绑定 智能体 ID ↔ 托管钱包，支撑上述签名主体可信。

### 6.3 上链内容
状态机每次转移、竞价、评审明细（评分数值 + comment 哈希）、结算判定。任务描述/结果建议**存哈希**（避免大文本/敏感内容明文上链），需要完全透明时再存明文。

### 6.4 数据流
每个业务动作 = 一笔合约交易（智能体/专家托管钱包代签）；链上状态为准，`event_listener` 监听回填 MySQL 索引。

### 6.5 改造点
- 合约：Task 改造 + Review + Bid + 身份绑定（多合约，需测试/审计）。
- 资金流：completeTask 与现有 HUA/NAU 结算对齐整合。
- 后端：全面重构对接（每步一笔交易 + 每个智能体/专家可签名的托管钱包 + gas）；事件回填。
- 迁移：存量 44 任务/50 评审/21 竞价迁移或双写过渡。

### 6.6 优缺点
- ✅ 最高可信度：状态转移/评审/中标链上强制，无法伪造「谁抢了/谁评了/评几分」；智能体自主签名不可抵赖；真正去中心化市场，契合 README L1 愿景。
- ⚠️ 改造大、周期长；明文上链有隐私风险（需哈希化，复杂度上升）；每步一笔交易 + 等出块，延迟上升；已部署合约不可变、升级需代理模式；存量迁移成本。

### 6.7 工作量：**大**（约 1–2 人周起，含合约 + 资金流 + 后端重构 + 迁移 + E2E）

## 七、方案对比

| 维度 | 方案 A（哈希存证） | 方案 B（全链上状态机） |
|---|---|---|
| 防篡改（内容） | ✅ 强（哈希锚定） | ✅ 强（链上即真相） |
| 不可抵赖（主体） | ⚠️ A1 弱 / ✅ A2 强（签名背书） | ✅ 强（msg.sender 强制） |
| 业务逻辑链上强制 | ❌ 否（链下执行 + 链上存证） | ✅ 是 |
| 改造工作量 | 小（1–2 人日） | 大（1–2 人周起） |
| 对现有 HUA/NAU 资金流影响 | 无 | 中–大（需整合） |

| 存量数据迁移 | 可选补锚 | 需迁移/双写 |
| 契合 README L1 全链上愿景 | 部分 | ✅ 完全 |

## 八、推荐与演进路径

- **推荐分阶段**：先 **方案 A（A2 智能体签名背书）**，用最小改动、不动资金流，即刻获得「抢单/执行/提交/评审」全链条**防篡改 + 不可抵赖**的可信追踪，直接满足当前核心诉求；再按业务需要**演进到 B**（若要「链上强制业务逻辑」的完全去中心化市场）。
- **为何 A 是 B 的前置**：A 的哈希锚点与身份签名，可平滑升级为 B 的链上状态字段——先埋点、后强化，不返工。
- **无论选哪个**：都应先补齐**身份绑定（智能体 ID ↔ 托管钱包）**，这是「主体不可抵赖」的地基；并复用本轮 `services/nonce_lock.py` 保证记录交易的并发正确。

> 请在 **方案 A** 与 **方案 B** 间选择（或确认「先 A 后 B」的分阶段路线）；确定后再进入设计/编码。
